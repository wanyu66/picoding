## 主要发现

- 不同 eventId 的同用户同文章重复点赞：每档 400 次调用，业务预期 2 分；10 并发实际 800 分，多计 399 次；50 并发实际 800 分，多计 399 次；100 并发实际 774 分，多计 386 次；200 并发实际 766 分，多计 382 次。MySQL 日志也记录这些重复行为，重建会保留错误积分。因此恢复前后一致不等于业务正确。此测试直接调用计分服务；HTTP/足迹生产端并发幂等性 N/A，不能据此断言完整 API 一定发生同样的重复。
- 同一个 eventId 重投与直接 Lua 重投独立验证；真实 Lua 使用同一份业务源码，通过独立预期 2 分核对。Lua 原子执行使“检查去重＋修改积分”不可交错；eventId 的稳定性及业务状态去重由应用负责。换一个 ID，Lua 无法知道是同一业务操作。
- MySQL 是事实源；Redis 故障期间服务无异常返回并不代表即时计分成功，必须看 pending 和补偿后分值。这里是真实停机/启动专用 Redis，直接触发补偿，不包含默认定时任务等待时间。
- 50-hot_member：2/400 次调用失败，其中 MySQL 死锁 2 次，无异常返回率 99.50%。MySQL 实际日志 398 条；重建只能重放已提交日志，不能补回未提交的请求。测试没有添加重试掩盖失败，原始异常见该场景 latencies.json。

- 非原子 ZSCORE/ZADD 对照会丢更新；实际 Lua 做更多元数据工作，功能成本不同，不能把二者 TPS 比值当性能提升百分比。生产计分服务还使用实例级同步锁，因此直接 Lua TPS 也不是业务服务 TPS。

## 结论边界及下一阶段

Lua 解决共享 Redis 状态操作被并发交错造成的丢更新，并把基于 eventId 的去重检查与计分绑定为原子步骤。业务幂等性解决同一次业务行为被重复接收或重试后不重复生效，需要稳定事件 ID、生产端状态保护及数据库约束。二者都不能单独保证 MySQL/Redis 的跨存储一致性，当前实现使用日志补偿提供恢复路径。

尚未验证：完整 HTTP→足迹→Outbox→Rabbit 链路、多 JVM、在线重建、数据库提交回滚与 Redis 投影的窗口、事件乱序、跨日/月撤销、Redis Cluster。热点文章对应的真实用户榜已测，独立文章积分榜不存在。建议下一阶段先验证生产端并发重复点赞及多实例重建，不修改业务逻辑来美化结果；随后以相同功能、相同持久化设置、同机多轮长时间测试取得可比较基线。
