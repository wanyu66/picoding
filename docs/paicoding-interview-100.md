# PaiCoding 项目亮点面试题与参考答案（100 题）

> 本文依据当前 PaiCoding 仓库实现整理，重点覆盖 Redis、Elasticsearch、RabbitMQ、事务 Outbox、数据一致性及故障治理。参考答案采用“先给结论，再说明项目实现与取舍”的表达方式，适合项目面试复习。涉及性能提升的数据必须以实际压测结果为准，不建议在面试中虚构 QPS、耗时或命中率。

## 一、项目与架构（1～10）

### 1. 请简要介绍 PaiCoding 项目。

PaiCoding 是一个基于 Spring Boot 2.7 和 Java 8 的技术内容社区，包含文章发布、审核与搜索，评论回复、点赞收藏、用户关注、消息通知、阅读统计、活跃度排行以及登录会话等功能。项目采用 Maven 多模块分层架构，并使用 MySQL 保存核心事实数据、Redis 承担高频状态和查询投影、Elasticsearch 提供全文检索、RabbitMQ 分发领域事件。

### 2. 项目为什么采用多模块架构？

项目拆分为 `paicoding-api`、`paicoding-core`、`paicoding-service`、`paicoding-ui` 和 `paicoding-web`。API 模块承载实体、DTO、VO 和枚举；Core 提供缓存等基础能力；Service 实现业务与数据访问；UI 管理前端资源；Web 提供控制器和应用入口。这种拆分能约束依赖方向、减少循环依赖，并让通用能力与具体业务解耦。

### 3. MySQL、Redis、Elasticsearch 和 RabbitMQ 在项目中的职责如何划分？

MySQL 是文章、用户、互动关系、领域事件和排行榜行为日志的事实数据源；Redis 保存阅读计数、排行榜、会话索引、搜索热词与短期缓存；Elasticsearch 保存面向检索的文章文档；RabbitMQ 将互动和文章变更分发给通知、统计、排行与搜索消费者。整体上是“数据库保证事实、缓存和索引提升读取、消息驱动派生数据”的设计。

### 4. 项目中哪些数据要求强一致，哪些接受最终一致？

用户关系、点赞收藏状态、评论、文章状态等核心业务写入首先在 MySQL 事务内完成，要求事务一致性。通知、统计、排行榜和 ES 索引属于可重试、可重建的派生数据，允许短时间延迟，通过 Outbox、幂等消费和补偿任务达到最终一致。

### 5. 为什么不在业务请求中同步完成通知、统计、排行和索引更新？

同步执行会延长核心写请求耗时，并让请求同时依赖 Redis、ES 和通知模块的可用性。项目把业务事实与领域事件写入同一个数据库事务，再异步更新各类派生数据，使核心写链路更短，也让各消费者能独立重试和故障隔离。

### 6. 项目的典型事件链路是什么？

以点赞为例：业务事务先修改 MySQL 中的点赞关系，同时向 `domain_event_outbox` 写入带唯一 `eventId` 的领域事件；Outbox 发布器将事件投递到 RabbitMQ；通知、统计和活跃排行队列分别消费；消费者通过“消费者名称 + 事件 ID”去重，然后完成自己的本地更新。

### 7. 项目如何避免“为了用中间件而用中间件”？

每个中间件都有明确的数据模型与恢复边界：Redis 用于原子计数、ZSet 排行和短期状态；ES 用于多字段中文全文检索；RabbitMQ 用于一对多异步事件分发。核心事实仍落在 MySQL，因此缓存、索引或消息处理异常时存在降级、重试或重建路径。

### 8. 项目中最值得讲的三项技术亮点是什么？

第一，MySQL 行为日志作为事实源、Redis ZSet 作为可重建排行榜投影，并用 Lua 保证多键更新原子性。第二，ES 使用中文/拼音分析、`search_after`、熔断降级和版本化索引 Alias 切换。第三，RabbitMQ 配合事务 Outbox、Publisher Confirm、幂等消费、重试和死信队列形成可靠事件链路。

### 9. 如何理解项目里的“事实数据”和“查询投影”？

事实数据描述真实发生过的业务，例如用户完成一次点赞或文章变为上线状态，适合持久化在 MySQL。查询投影是为了某类读请求构建的派生结构，例如 Redis 排行榜和 ES 搜索文档；投影丢失时可以从事实数据重新生成，因此不应成为唯一数据源。

### 10. 如果让你继续演进该架构，会先做什么？

优先补齐可观测性和自动化运维：为 Outbox 堆积、MQ 重试和 DLQ、Redis 同步延迟、ES 索引覆盖率和熔断状态建立指标与告警；然后增加故障演练和端到端压测，用真实数据确定批大小、并发度、TTL 和限流阈值。

## 二、Redis 设计与实现（11～35）

### 11. Redis 在 PaiCoding 中有哪些主要使用场景？

主要包括文章阅读计数、用户与文章统计缓存、日/月活跃排行榜、JWT 会话与用户 Token 反向索引、白名单、短链接、搜索热词与搜索结果缓存、接口去重、LLM 使用量限制，以及流式聊天事件回放等。

### 12. 项目为什么封装 `RedisClient`？

`RedisClient` 对 String、Hash、Set、ZSet、List、HyperLogLog、Pipeline 和 Lua 脚本提供统一静态入口，并统一 key 前缀和序列化。业务代码不必重复处理字节转换和模板调用，但静态工具会降低可测试性和依赖显式性，后续可演进为可注入的领域缓存组件。

### 13. 为什么文章阅读量不直接每次更新 MySQL？

阅读是高频、允许短暂延迟的计数场景。如果每次访问都更新同一数据库记录，会产生热点行竞争和大量随机写。项目先用 Redis Hash 的 `HINCRBY` 原子累加，再由定时任务批量同步到 MySQL，削峰并降低数据库写压力。

### 14. 一次文章阅读为什么使用 Pipeline？

阅读行为需要同时增加文章维度和作者维度的统计值。Pipeline 可以把多个 Redis 命令一次发送，减少网络往返；但 Pipeline 只优化传输，不保证多条命令作为一个事务原子执行。如果要求跨 key 强原子，应改用 Lua。

### 15. 阅读计数如何同步回数据库？

定时任务每 5 分钟使用 `SCAN` 查找文章统计 key，读取 Redis 中的阅读总数，再把数据库计数更新为目标总数。采用“写最终值”而不是“按差值累加”，可降低任务重复执行导致重复加计数的风险。

### 16. 为什么使用 `SCAN` 而不是 `KEYS`？

`KEYS` 会一次遍历整个 key 空间，数据量大时可能长时间阻塞 Redis。`SCAN` 以游标增量遍历，单次工作量可控，更适合线上任务。需要注意 `SCAN` 可能返回重复项且不提供严格快照语义，因此处理逻辑应幂等。

### 17. Redis 计数同步任务会不会丢数据？

任务读取某一时刻的 Redis 总数并写入 MySQL，读取之后新增的计数仍保留在 Redis，下次会写入更大的总数，因此正常并发下不会因为覆盖式同步而丢失新增量。需要确保数据库更新语义是单调的，避免旧任务把更大的值覆盖成更小的值。

### 18. 如何进一步增强阅读计数同步的并发安全？

可以在 SQL 中使用 `GREATEST(db_count, redis_count)` 保证单调更新，或记录同步版本/时间戳；多实例定时任务可增加分布式锁或任务分片。若需要精确增量，可用 Lua 原子交换计数桶，但必须处理交换后数据库写失败的补偿。

### 19. 活跃排行榜为什么适合使用 Redis ZSet？

ZSet 同时保存成员和分值，天然支持按分值排序、查询 Top N、查询个人分数与排名，时间复杂度适合高频排行读写。项目用用户 ID 作为 member，活跃积分作为 score，分别维护日榜和月榜。

### 20. 排行榜为什么仍然保存 MySQL 行为日志？

Redis 是内存系统，可能因误删、过期或故障丢失榜单。项目将行为事件写入 MySQL，并标记是否已投影到 Redis，因此 MySQL 是事实源，Redis 只是可重建投影；投影失败时可以定时重放，榜单缺失时可以重建。

### 21. 排行榜 Lua 脚本解决了什么问题？

一次积分事件需要完成事件去重、撤销校验、日榜更新、月榜更新、首次达分时间记录、就绪标记和 TTL 设置。Lua 在 Redis 单线程内原子执行这些操作，避免应用执行多条命令时出现只更新一部分数据的中间状态。

### 22. 排行榜如何实现事件幂等？

Lua 脚本先在事件 Hash 中执行 `HEXISTS`；如果 `eventId` 已存在就直接返回，不再次修改积分。MySQL 行为表也对事件 ID 做唯一约束，两层去重分别保护事实记录和 Redis 投影。

### 23. 取消点赞时如何防止重复扣分？

取消事件要关联原始加分事件。业务层校验原事件存在、属于同一用户和目标、尚未被取消；Lua 再检查 Redis 事件状态，并把原事件标记为已取消。重复取消或找不到有效原事件时不会继续扣分。

### 24. 为什么取消操作要回写原行为所属日/月？

如果用户隔天取消昨天的点赞，把负分记到今天会污染今天的行为榜，并使月内统计难以解释。项目让撤销事件继承原事件的日桶和月桶，从原积分产生的周期中扣除，保持时间维度语义正确。

### 25. 同分用户如何稳定排序？

项目除 ZSet 分数外，还用 Hash 记录用户首次达到某分值的时间。查询后按积分降序、首次达分时间升序等规则二次排序，使同分结果更稳定。大规模场景可把时间编码进复合 score，但要注意浮点精度和分数边界。

### 26. 月榜是如何生成的？

项目既在事件发生时更新当月 ZSet，也提供 Lua 汇总逻辑，通过 `ZUNIONSTORE ... AGGREGATE SUM` 聚合每日榜单，并设置月榜就绪标记和过期时间。定时汇总与重建机制用于修复缺失或不完整投影。

### 27. Redis 排行榜过期策略如何设计？

日榜和对应的同分辅助结构按天设置保留期，月榜按月设置保留期；脚本统一设置绝对过期时间，避免相关 key 的生命周期不一致。过期时间应覆盖产品查询窗口，并留出故障恢复和迟到事件处理的缓冲期。

### 28. 排行榜投影到 Redis 失败怎么办？

MySQL 事件记录保留 `redis_applied=0` 状态，定时恢复任务扫描未应用事件并重放。Redis 榜单或就绪标记缺失时，可根据 MySQL 行为日志重建指定月份，从而把 Redis 故障降级为可恢复的投影异常。

### 29. 项目如何用 Redis 配合 JWT 实现主动登出？

JWT 本身无状态，签发后无法直接撤销。项目把 Token 到用户 ID 的映射写入 Redis，并让 TTL 与 JWT 有效期一致；请求既验证 JWT 签名和过期时间，也检查 Redis 映射。登出时删除映射，Token 即使尚未过期也会失效。

### 30. 如何实现按用户批量踢下线？

项目用 Redis Set 保存 `userId -> tokens` 的反向索引，登录时加入 Token，登出时移除。管理员踢人时直接读取该 Set 并逐个删除 Token，复杂度与该用户会话数相关；旧版本没有索引时才回退到 `SCAN` 全局查找。

### 31. 多设备登录限制是如何实现的？

项目为 Token 保存设备 ID、User-Agent 哈希、IP、地区和最近访问时间等元数据。登录时读取该用户的 Token Set，清理失效会话并按设备归组；超过最大设备数时淘汰最早登录设备对应的会话。

### 32. `SET NX + TTL` 在项目中有哪些用途？

它用于微信回调去重、会话访问落库节流以及用量限制等场景。`SET NX` 保证同一 key 在有效期内只有第一次操作成功，TTL 避免锁或标记永久残留；设置值与过期时间必须通过一条原子命令完成。

### 33. 如何防止缓存穿透、击穿和雪崩？

当前项目已有 TTL、请求去重和部分降级能力。进一步可对不存在数据缓存短期空值防穿透，对热点重建使用互斥锁或逻辑过期防击穿，对 TTL 增加随机抖动并分批预热防雪崩；关键路径还应在 Redis 异常时回退数据库或本地能力。

### 34. 项目中的搜索热词如何使用 Redis？

搜索词和零结果词使用 ZSet 按次数累计，点击行为使用 Hash 计数。接口读取 ZSet Top N 生成热门查询和前缀建议；这些数据属于体验优化，Redis 异常时返回空列表，不影响核心搜索。

### 35. Redis 故障时系统应如何降级？

需要按数据性质区分：搜索热词、流式回放等增强能力可以直接关闭；会话校验属于安全链路，通常应失败关闭而不能绕过；阅读计数可临时丢弃或写本地队列；排行榜依靠 MySQL 行为日志恢复。降级策略不能一概而论。

## 三、Elasticsearch 搜索体系（36～65）

### 36. 项目为什么引入 Elasticsearch？

MySQL 的模糊查询难以高效支持文章标题、摘要和正文的中文分词、多字段相关性、同义词、拼音和高亮。Elasticsearch 倒排索引能提供更好的召回、排序与扩展能力，因此项目把它作为文章搜索引擎，而不是核心事实数据库。

### 37. ES 中索引了哪些文章字段？

主要包括文章 ID、作者、标题、短标题、摘要、正文、状态、删除标记、分类/专栏等结构化字段，以及质量分、阅读量、点赞量和创建更新时间。文本字段用于召回，结构化字段用于过滤，质量和热度字段参与排序。

### 38. 项目的中文分词方案是什么？

索引阶段使用 `ik_max_word` 获得更细粒度词项，查询阶段使用 `ik_smart` 控制查询词数量；同时加入小写、停用词和同义词过滤器。这样在召回率和查询成本之间取得平衡，但依赖 ES 集群安装 IK 等插件。

### 39. 为什么索引分析器和搜索分析器不同？

索引时细分可以保存更多可能匹配的词项，提高召回；搜索时相对粗分可减少无意义组合，改善精确度和性能。两者必须保证产生的词项存在可匹配交集，否则会出现有文档却搜不到的问题。

### 40. 项目如何支持拼音搜索？

文本字段增加 `.pinyin` 子字段，并配置拼音过滤器保留全拼、首字母和原始词。查询时可同时匹配中文主字段和拼音子字段，因此用户输入全拼或首字母也有机会召回文章。

### 41. 同义词是如何处理的？

搜索分析器使用 `synonym_graph`，配置 JVM/Java 虚拟机、MQ/消息队列、ES/Elasticsearch 等领域同义词。它能提升技术词汇的召回，但同义词表更新、图结构查询和多词同义词都需要测试，生产环境更适合通过可维护词典管理。

### 42. 项目如何设计多字段权重？

标题和短标题权重最高，摘要次之，正文最低；短语匹配会获得更高 boost，前缀和模糊匹配权重相对较低。这样优先返回标题直接相关的内容，同时保留正文召回能力。

### 43. `match_phrase`、`match_phrase_prefix` 和模糊匹配分别解决什么问题？

`match_phrase` 强调词序和连续性，适合精确短语；`match_phrase_prefix` 支持最后一个词的前缀扩展，适合输入提示；模糊匹配通过编辑距离容忍少量拼写错误。三者组合时要控制 boost 和扩展数量，避免噪声和高开销。

### 44. `function_score` 在项目中如何使用？

基础文本相关性之外，项目把质量分、阅读量、点赞量和时间等业务信号作为加分函数，并采用 `score_mode=sum`、`boost_mode=sum`。它让结果兼顾“搜得准”和“内容质量”，但需要防止热度完全淹没文本相关性。

### 45. ES 查询为什么还要使用 filter？

文章是否上线、是否删除、作者 ID、栏目 ID 等是精确条件，不需要参与相关性评分。放入 bool filter 语义更清楚，并可利用过滤缓存；文本相关条件则放在 must/should 中计算 `_score`。

### 46. 搜索高亮是怎么做的？

请求为标题、短标题、摘要和正文配置前后标记、片段长度与片段数量，响应再转换为带字段名称的摘要片段。输出到页面前需要进行 HTML 转义，只保留服务端生成的高亮标记，避免文章内容造成 XSS。

### 47. 为什么使用 `search_after` 处理分页？

深分页使用 `from + size` 时，每个分片需要保留并排序前面所有命中，页码越大成本越高。`search_after` 使用上一页最后一条记录的排序值继续查询，资源开销更稳定，适合连续翻页。

### 48. `search_after` 有哪些限制？

它不能直接随机跳到任意页，必须持有前一页游标；排序字段必须稳定且包含唯一兜底字段，否则同分文档可能重复或遗漏。搜索期间索引发生变化还可能导致视图漂移，严格一致的长分页可配合 PIT。

### 49. 项目如何兼容传统页码与 `search_after`？

服务端把每页的下一游标写入 Redis，后续页根据关键词和查询体读取对应页游标。若游标缺失就返回空结果或触发降级，因此该方案适合正常顺序翻页，不承诺任意页随机访问。

### 50. 为什么限制最大搜索页数？

项目通过 `search-max-page` 限制页码，避免爬虫或异常请求无限拉取结果，也减少游标缓存数量和 ES 压力。若用户需要浏览大量结果，应改进查询条件、使用筛选或提供专门的导出任务。

### 51. 搜索结果缓存如何设计？

第一页结果按规范化关键词和查询体生成缓存 key，并设置较短 TTL；分页游标也放入 Redis。缓存 key 还包含索引 generation，重建切换或索引结构变化后更新 generation，即可让旧缓存自然失效。

### 52. 为什么只重点缓存第一页？

用户访问和重复搜索主要集中在第一页，缓存收益最高。缓存所有深分页会产生大量低复用 key，还会增加失效和一致性成本，因此项目选择优先优化高频路径。

### 53. ES 不可用时如何降级？

服务会判断 ES 开关、客户端、索引覆盖率和熔断状态。如果 ES 不可用、索引不完整或请求失败，就返回空的 ES 结果标识，由上层使用 MySQL 标题检索兜底，确保搜索入口仍可使用，只是能力退化。

### 54. 项目中的 ES 熔断机制是什么？

服务记录连续搜索失败次数，达到阈值后在一段时间内拒绝继续访问 ES，并直接走 MySQL 降级；熔断时间结束后允许探测请求，成功则恢复。它避免 ES 故障时每个请求都等待超时并进一步放大故障。

### 55. 熔断和限流有什么区别？

限流关注请求量是否超过系统容量，即使依赖健康也可能拒绝流量；熔断关注依赖近期是否持续失败，在故障窗口内快速失败。搜索服务通常同时需要入口限流、ES 客户端超时和故障熔断。

### 56. 文章变化如何增量同步到 ES？

文章创建、更新、审核、上下线和删除会形成统一领域事件，由搜索队列消费者处理。删除事件从索引删除文档，其他事件重新查询 MySQL 中的完整搜索文档；若文章已删除或非上线状态，也执行删除。

### 57. 为什么消费者重新查 MySQL，而不是直接用事件里的文章全文？

事件只携带标识和必要上下文，消费者从事实源构建当前完整文档，可以减少消息体积和事件版本耦合，也能合并短时间内的多次更新。代价是增加数据库读取，并且必须用版本控制避免旧事件覆盖新状态。

### 58. 项目如何防止乱序事件覆盖新索引？

Bulk 和单文档写入使用基于文章更新时间生成的外部版本，并设置 `version_type=external_gte`。ES 只接受版本不小于当前文档的写入，从而降低旧事件迟到造成状态回退的风险。

### 59. 为什么需要全量重建索引？

字段 mapping、分析器或同义词变化通常不能直接安全修改现有索引；历史增量同步也可能因故障产生遗漏。全量重建能基于 MySQL 当前事实生成一致的新索引，并作为一致性修复手段。

### 60. 全量重建为什么按主键游标扫描 MySQL？

`WHERE id > lastId ORDER BY id LIMIT batchSize` 的性能比大 offset 分页更稳定，也不需要数据库跳过大量旧行。前提是排序主键单调且查询期间正确处理新增、删除和更新。

### 61. 全量重建为什么使用 Bulk API？

逐条索引会产生大量 HTTP 往返和刷新开销。Bulk 把一批 NDJSON 操作一次提交，可显著提高吞吐；项目会检查响应中的 `errors`，并记录首个批次错误，而不能只看 HTTP 200。

### 62. 重建过程中发生文章更新怎么办？

项目在存在活动重建目标时，对当前线上索引和新版本索引执行双写；删除也同时作用于两个索引。完成批量扫描和失败检查后再切换 Alias，从而缩小全量扫描期间增量变化造成的不一致窗口。

### 63. 为什么使用版本化索引和 Alias 原子切换？

直接清空线上索引再重建会导致搜索不可用或数据残缺。项目创建带时间版本的新索引，旧 Alias 继续服务；新索引构建成功并刷新后，通过一次 `_aliases` 请求删除旧绑定并添加新绑定，实现近似无停机切换。

### 64. 重建失败时如何处理？

Bulk 批次按配置次数重试，仍失败则记录失败区间并将任务标为失败，不切换 Alias；管理员可以重试失败批次或终止任务。核心原则是“新索引不完整就绝不替换当前可用索引”。

### 65. 如何校验 MySQL 与 ES 的一致性？

可以比较可搜索文章总数与索引文档数，并按文章 ID 抽样或分批核对关键字段和更新时间。项目提供索引覆盖状态和一致性报告能力；发现差异后可单文档修复，差异较大时触发全量重建。

## 四、RabbitMQ、Outbox 与领域事件（66～90）

### 66. RabbitMQ 在项目中承担什么职责？

RabbitMQ 将点赞、收藏、评论、回复、关注以及文章生命周期事件异步广播给通知、统计、活跃排行和搜索模块。它承担的是业务解耦和削峰，不作为业务事实的唯一存储。

### 67. 为什么设计统一领域事件？

统一事件包含 `eventId`、事件类型、操作者、目标、发生时间、版本和 `traceId`。生产者和消费者共享稳定信封，新消费者可以订阅同一事件而无需修改核心写链路，也便于幂等、追踪和版本演进。

### 68. 为什么一个交换机绑定多个业务队列？

同一个领域事件需要被通知、统计、排行和搜索独立处理。如果共用一个队列，消息只会被其中一个消费者取走；绑定多个队列可实现发布一次、每个业务各消费一次，并让失败和扩容互不影响。

### 69. 项目为什么使用 Direct Exchange？

当前领域事件统一使用固定 routing key，并把多个明确队列绑定到该 key，Direct Exchange 已满足确定路由需求。若未来按 `article.*`、`interaction.*` 等模式订阅，可改用 Topic Exchange 提升路由灵活性。

### 70. 什么是事务 Outbox？

事务 Outbox 是在业务数据库事务中同时写业务数据和待发布事件表，事务提交后由独立发布器把事件发送到 MQ。它解决“数据库提交成功但消息没发出”或“消息发出但数据库回滚”的双写不一致问题。

### 71. Outbox 为什么能保证业务数据和事件的一致性？

两者位于同一个 MySQL 本地事务：要么业务数据和事件记录一起提交，要么一起回滚。它不保证消息只发送一次，但保证已提交业务最终存在可发送的事件，之后通过重试和消费幂等实现至少一次语义。

### 72. Outbox 表有哪些关键字段和索引？

包括唯一 `event_id`、事件类型、聚合类型与 ID、JSON payload、状态、重试次数、下次重试时间、发布时间、错误信息和创建更新时间。`event_id` 唯一约束防止重复事件记录，`status + next_retry_time + id` 索引支持扫描待发布任务。

### 73. Outbox 发布器如何抢占任务？

发布器先用条件更新把记录从 `PENDING/FAILED` 改为 `SENDING`，只有更新行数为 1 的实例获得发送权。该方式能降低多实例定时任务重复发送，但在网络超时等不确定结果下仍可能重复，因此消费者必须幂等。

### 74. 为什么要恢复长时间处于 `SENDING` 的记录？

发布实例可能在抢占后宕机，使记录永久卡在 `SENDING`。项目把更新时间超过 5 分钟的记录改回失败并重新调度，这相当于发送租约；租约长度要大于正常发送确认耗时。

### 75. Outbox 发送失败如何重试？

失败后增加 `retry_count`，计算指数退避时间并写入 `next_retry_time`，最大延迟封顶。指数退避可以避免 MQ 故障时发布器持续高频打满依赖；还应对最大重试次数和长期失败记录建立告警或人工处理流程。

### 76. Publisher Confirm 解决什么问题？

Confirm 表示消息是否到达 RabbitMQ Exchange。项目启用 correlated confirm，并用 `eventId` 作为 CorrelationData，发布器最多等待确认 5 秒；收到 nack 或超时就把 Outbox 标为失败并重试。

### 77. Publisher Return 解决什么问题？

消息可能成功到达 Exchange，却因为 routing key 没有匹配队列而被丢弃。项目设置 `mandatory=true` 并启用 Returns Callback；发现 returned message 时不把 Outbox 标记为成功，从而覆盖“到 Exchange 但未路由”的漏洞。

### 78. 为什么消息还要设置持久化？

持久化消息与 durable Exchange/Queue 配合，可降低 Broker 重启时消息丢失概率。但持久化不等于绝对不丢，仍需要镜像/仲裁队列、磁盘可靠性、发布确认和正确的集群策略。

### 79. 项目的消息投递语义是什么？

整体是至少一次投递。发送确认结果不确定、Outbox 租约恢复或消费者处理后 ACK 前宕机，都可能造成重复消息；项目不追求昂贵的全局 exactly-once，而通过唯一事件 ID 和幂等业务实现“效果上的一次”。

### 80. 消费端如何实现幂等？

消费前向 `domain_event_consume` 执行 `INSERT IGNORE`，主键是 `consumer_name + event_id`。插入成功才执行 handler；重复消息插入失败后直接返回。不同消费者名称彼此独立，因此同一事件仍能被通知、排行、统计和搜索各处理一次。

### 81. 为什么幂等记录和业务处理要在同一事务中？

如果先提交幂等记录再处理业务，处理失败后重试会被误判成已完成；如果先处理业务再单独写幂等记录，宕机可能重复处理。项目用 `@Transactional` 包裹插入记录和 handler，成功一起提交、异常一起回滚。

### 82. 仅靠消费记录表是否足够？

它能保护同一消费者的一般重复消息，但业务表仍应有自然唯一约束，例如通知的事件 ID、业务 key、点赞关系等。双层约束可以防止代码缺陷、并发竞态或其他写入口绕过消费框架。

### 83. 消费失败后如何重试？

监听容器配置无状态重试，最多尝试 3 次，退避时间从 500ms 开始按 2 倍增长并封顶 5 秒。短暂数据库或网络异常可在消费者本地快速恢复，持续失败则进入死信流程。

### 84. 为什么要设置 `defaultRequeueRejected=false`？

如果失败消息一直重新入原队列，会形成无间隔死循环，阻塞正常消息并持续消耗资源。关闭默认 requeue 后，重试耗尽的消息被拒绝并根据队列参数路由到 DLX/DLQ。

### 85. 为什么每类消费者使用独立死信队列？

通知、统计、排行和搜索的失败原因、修复方式和重放风险不同。独立 DLQ 便于分别告警、排查和回放，也避免某一业务的大量毒消息淹没其他业务。

### 86. DLQ 中的消息应该如何处理？

先记录队列、事件 ID、异常和重试次数，修复根因后通过受控工具重放到原交换机或指定队列。重放前必须确认消费者幂等，且不能不加判断地自动无限回灌，否则可能形成故障循环。

### 87. `traceId` 为什么要放入事件和消息头？

异步链路跨越 HTTP 请求、数据库 Outbox、发布器和多个消费者，线程上下文无法自动传递。显式保存 `traceId` 可以把生产日志、Outbox 状态、MQ 发布和消费日志串联起来，缩短问题定位时间。

### 88. 如何处理消息顺序问题？

项目主要依赖事件幂等和业务当前状态重查，而不是假设全局有序；ES 写入还使用外部版本防旧事件覆盖。若某一聚合确实要求严格顺序，可按聚合 ID 路由到固定分区/队列并串行消费，但会牺牲并行度。

### 89. RabbitMQ 关闭时系统还能运行吗？

配置开关可关闭 RabbitMQ 自动配置，但需要明确业务退化：核心 MySQL 写入可以继续，通知、统计、排行和 ES 增量同步会延迟。如果关闭时仍写 Outbox，重新启用后可补发；若相关 Bean 被条件禁用，启动依赖也必须正确处理。

### 90. 如何监控 RabbitMQ 事件链路？

应监控 Outbox 各状态数量和最老待发时间、Confirm nack、Return 次数、发布延迟、队列深度、消费速率、重试和 DLQ 数量，并按事件类型统计端到端耗时。项目已有发布确认、退回、重试和死信监控记录点，可进一步接入 Micrometer 与告警平台。

## 五、综合一致性、故障与面试追问（91～100）

### 91. 如何描述项目的端到端最终一致性？

核心业务和 Outbox 在 MySQL 本地事务内强一致；Outbox 至 RabbitMQ 采用确认与重试；RabbitMQ 到消费者采用至少一次投递；消费者通过幂等表和业务唯一键防重复；Redis 与 ES 作为投影还支持定时恢复、校验和重建。每一段都有明确失败状态和补偿路径。

### 92. 如果 MySQL 提交成功后应用立即宕机，会发生什么？

Outbox 记录已经随业务事务提交，因此事件不会因应用宕机消失。应用恢复后定时发布器扫描 `PENDING` 记录并发送；这正是 Outbox 相比事务提交后直接调用 RabbitMQ 的优势。

### 93. 如果 Broker 已收到消息，但发布器等待 Confirm 超时，会发生什么？

发布器会把 Outbox 标为失败并再次发送，因此 Broker 可能收到重复消息。这是典型的不确定提交窗口，不能通过发布端完全消除；消费者必须用 `eventId` 幂等，才能保证重复投递不产生重复业务效果。

### 94. 如果消费者完成业务更新后、发送 ACK 前宕机，会发生什么？

RabbitMQ 会重新投递消息。由于消费记录与业务更新在同一数据库事务中，如果事务已提交，重投时唯一键使 handler 不再执行；如果事务未提交，重投会正常重新处理。

### 95. 如果 Redis 排行榜被误删，如何恢复？

检测到榜单 key 或就绪标记缺失后，按时间桶读取 MySQL 行为事件，重新执行投影逻辑生成日榜/月榜；恢复期间可以暂时返回空榜或历史快照。恢复完成后设置标记和 TTL，并核对事件数及 Top N。

### 96. 如果 ES 索引被误删，如何恢复？

搜索先熔断并降级到 MySQL 标题查询；后台创建新的版本化索引，按主键游标扫描 MySQL 并 Bulk 写入，同时接收增量事件双写；校验完成后通过 Alias 原子切换恢复服务。

### 97. Redis、ES 和 MQ 同时故障时，核心业务还能否写入？

在 MySQL 可用且代码没有同步强依赖这些中间件的前提下，文章和互动事实以及 Outbox 仍可提交。搜索、排行榜、通知和部分统计会降级或延迟；恢复后再补发 Outbox、重放投影和重建索引。会话鉴权若依赖 Redis，应按安全原则拒绝无法确认的会话。

### 98. 如何对这套架构做压测？

分别建立阅读热点写、点赞/取消并发、排行榜 Top N、中文搜索、深分页和领域事件突发流量场景，再进行混合压测。观察 MySQL 锁等待、Redis 延迟与热 key、ES P95/P99 和拒绝数、Outbox 堆积、MQ 队列深度及端到端最终一致延迟，不能只看接口平均响应时间。

### 99. 面试中如何回答“项目提升了多少性能”？

如果没有真实压测数据，应说明设计目标和验证方法，不要编造数字。例如：“阅读计数从每次同步写 MySQL 改为 Redis 原子累加和五分钟批量回写，减少热点行写入；具体提升需要用同等数据量和并发模型进行对比压测。”有真实结果时再给出环境、数据规模、P95/P99 和错误率。

### 100. 用一分钟总结你在这个项目中的技术价值。

我重点解决了高频数据访问、全文检索和异步一致性三个问题：用 Redis 的 Hash、ZSet、Set、Pipeline 和 Lua 构建计数、可恢复排行榜与会话体系；用 Elasticsearch 的中文/拼音分析、相关性排序、`search_after`、熔断降级和 Alias 重建完善文章搜索；用 RabbitMQ 与事务 Outbox、发布确认、幂等消费、重试和 DLQ 解耦通知、统计、排行及索引同步，并为关键派生数据设计了校验和恢复路径。

## 面试使用建议

1. 不要逐字背答案，优先掌握“业务问题—技术方案—失败场景—设计取舍”四段式表达。
2. Redis 重点画出“业务事件 → MySQL 日志 → Lua 投影 → 定时恢复”的排行榜链路。
3. ES 重点说明“增量事件双写 + 新索引全量扫描 + 校验 + Alias 切换”。
4. RabbitMQ 重点说明 Outbox 解决双写问题，但整体仍是至少一次投递，必须依赖消费幂等。
5. 被问到性能数字时只使用真实压测数据，并同时交代机器配置、数据规模和统计口径。
