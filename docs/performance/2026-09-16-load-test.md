# PaiCoding 压测实测报告（2026-09-16）

已对本机运行中的文章列表、文章详情、搜索列表进行 HTTP 压测。两个实验共完成 **19 个计时阶段、34,661 次请求，其中 4,704 次业务失败**，不含预热及预检请求。两次实验均因详情接口错误率超过 5% 自动停止，未完成原定三轮全矩阵，不能据此宣称稳定容量或优化收益。

## 测试条件与请求分布

- 时间：北京时间 15:04–15:11；中间包含故障诊断和停止加压的间隔。
- 主机：Intel Core i7-14650HX，24 逻辑处理器，15.78 GiB 内存，Windows 10.0.26100。压测机与应用同机，其他本地软件/容器仍在运行。
- 客户端：Node.js v24.15.0。服务端：运行中的 Java 17.0.19，PID 3500，已通过 Get-Process 和 jcmd 核对。本次未重编译或重启服务端；仓库构建要求 Java 8，与当前运行环境不同。
- 工作区 HEAD：`65708a5985d7d637c86025c8933a7a106a9d8f46`，包含之前未提交的启动修复；不保证源码与已加载类完全一致。
- 首页公开可见文章只有 **8 篇**，`hasMore=false`；不是数据库总行数调查，不能外推到十万/百万级文章规模。
- 列表：`GET /article/api/list/data/category/0?page=1&size=10`，固定第一页。
- 详情：`GET /article/api/data/detail/{id}`，均匀轮询 `102,101,100,17,16,15,14,1`。
- 搜索：`GET /search/api/list?key={keyword}&page=1&size=10`，均匀轮询 `Java、技术派、分布式`。包含 HTML 模板渲染，不是单独的搜索引擎延迟。
- 所有实测搜索响应的 `searchState` 均为 `ES_UNAVAILABLE`；运行状态显示索引不可用，当前为 **MySQL 标题搜索回退**。
- 闭环、匿名、无思考时间，HTTP/1.1 keep-alive，无重试，不加载图片等浏览器子资源。10 秒请求截止时间；每阶段预热 3 秒、测量 10 秒。相邻轮反转场景和并发档顺序。
- 同时校验 HTTP 200、业务码 0 和响应内容，避免将 HTTP 200 的错误响应计为成功。读取详情会增加阅读计数；未清缓存、未造数、未禁用保护机制。

第一实验原计划 1/8/32 并发各三轮，完成 11/27 阶段后停止。第二实验降至 1/8 并发，完成 8/18 阶段后再次停止。因而本次是短时基线及故障发现测试，不是容量认证、长时间稳定性测试或生产流量模拟。

## 压测暴露的故障

| 实验阶段 | 成功 / 总数 | 业务失败 | 阶段错误率 | 成功 QPS |
|---|---:|---:|---:|---:|
| 第一实验，详情 32 并发第二轮 | 176 / 4042 | 3866 | **95.65%** | 17.46 |
| 第二实验，详情 8 并发第二轮 | 2964 / 3802 | 838 | **22.04%** | 296.17 |

失败响应是 HTTP 200、业务码 `100500001`。用户提供的对应控制台堆栈确认了直接失败路径：

```text
RedisCircuitBreaker$RedisCircuitOpenException: Redis circuit is open
RedisCircuitBreaker.acquirePermission(RedisCircuitBreaker.java:46)
RedisClient.executePipelined(RedisClient.java:58)
CountServiceImpl.incrArticleReadCount(CountServiceImpl.java:122)
ArticleReadServiceImpl.queryFullArticleInfo(ArticleReadServiceImpl.java:212)
ArticleRestController.detail(ArticleRestController.java:91)
```

读取详情同步增加 Redis 阅读计数，熔断异常未在该调用链中隔离，导致文章详情请求失败。这说明计数更新影响了主查询可用性；**首次使 Redis 熔断的异常尚未确认**，不能据此直接认定为连接池耗尽、Redis 容量不足或超时。仓库日志文件未记录压测时段异常，需补充熔断前日志。

停止压力后探测详情恢复正常。此次没有为提高数字而吞掉异常、禁用熔断或省略阅读计数。

## 关于“提升数字”的结论

**当前只能报告实测性能，不能声称 QPS 提升 X%、延迟降低 Y% 或搜索准确率提高 Z%。**

没有同一数据快照、相同运行条件下的优化前版本，也未执行优化后的版本。并发数变化、JIT/缓存预热或第二次测试变快，都不能作为代码优化收益。前几次启动修复只能证明应用能够继续启动，不能作为性能基线。

仓库 `scripts/search-evaluation` 的标注和样例结果使用模板 ID，尚无真实人工相关性评测集。因此未执行示例后将其结果冒充真实准确率；HTTP 成功率也不是搜索准确率。

可准确引用的表述：

> 在 i7-14650HX / 16GB 本机、8 篇公开文章的小数据集上，对文章列表、详情与搜索进行闭环压测，共记录 34,661 次计时请求。8 并发观测汇总中，列表约 126 QPS、P95 80ms，MySQL 回退搜索约 231 QPS、P95 65ms；详情虽有约 293 成功 QPS，但错误率 8.70%，定位到 Redis 阅读计数熔断异常影响详情可用性。该结果不是生产容量或优化提升承诺。

## 后续优化及同条件复测顺序

1. 优先补齐 Redis 初始失败、熔断状态、连接池等待时间和请求关联日志，确认首个触发原因。为阅读计数设计有明确持久化/补偿策略的失败处理，再验证详情可用性；不要以直接吞异常、丢计数换取 QPS。
2. 恢复 Elasticsearch 索引与覆盖率，固定文章数据和关键词，分别验证 ES 正常路径与 MySQL 降级路径。
3. 对列表逐篇补全标签、统计和作者的路径做 SQL/Redis 次数分析。当前实现存在逐篇处理，是否为主要瓶颈还需剖析证明。
4. 固定数据和请求分布，使用独立压测机、长测量窗口、交替 A/B 多轮对比，再计算 `QPS提升=(新-旧)/旧`、`延迟降低=(旧-新)/旧`，同时报告错误率和分位数。
